# Airflow: basic / starter

Вы пишете DAG целиком (задание 1) и четыре бизнес-функции (задания 2-5). Готового DAG в шаблоне нет.

Полное задание см. в [ASSIGNMENT.md](ASSIGNMENT.md). Модель уже обучена и приложена, скачивать датасеты и обучать её для выполнения ДЗ не нужно.

## Исходное состояние

- `dags/hw_basic.py` содержит только комментарий TODO (задание 1). Объявление DAG, три задачи extract/infer/publish и связи между ними вы пишете сами по ASSIGNMENT.md.
- `dags/batch_common.py` содержит готовые функции (артефакты, дата, модель, predict) и заглушки заданий 2-5.
- Сервисы запускаются и здоровы сразу. Файл DAG импортируется без ошибок, но DAG `hw_basic_batch_inference` отсутствует, поэтому в UI его пока нет. Это ожидаемо.
- `make check` падает с явным сообщением, что DAG не найден. `make test` падает на отсутствующем DAG и на незаполненных заданиях 2-5. Ненулевой код выхода здесь - нормальное исходное состояние; запускайте команды по отдельности, чтобы падение одной не мешало следующей.

## Запуск с нуля

Docker Desktop с Compose v2, Python 3 и make. На Windows по идее хватит терминала WSL2. Откройте терминал в этой папке. Команды выполняются на хосте, если явно не указано docker compose exec.

На Linux перед первым запуском запишите UID владельца файлов: `printf 'AIRFLOW_UID=%s\n' "$(id -u)" > .env`. Это создаёт локальный файл настроек и позволяет контейнеру писать артефакты. Без правильного UID на Linux `make clean` также может не суметь удалить созданные контейнером файлы из-за прав доступа. Если `.env` уже существует, измените в нём AIRFLOW_UID, не затирая остальные настройки. На macOS работает и без этой операции.

```bash
make up
make health
```

```bash
make check
```

```bash
make test
```

Первые две команды должны пройти. `make check` и `make test` до реализации падают, как описано выше.

UI: http://localhost:8090. PostgreSQL: localhost:5434, database warehouse, user/password etl/etl. HTTP: http://localhost:8001. Внутри контейнера адреса другие: warehouse:5432 и source-api:8000. Имена соединений Airflow warehouse и source_api, они уже переданы через переменные окружения, но могут не отображаться в списке сохранённых Connections UI.

## После реализации

Не снимайте паузу и не запускайте DAG, пока не выполнили задание 1, потому что запускать нечего. Когда `make check` проходит, DAG появляется в UI (обычно 10-30 секунд после сохранения файла) на паузе. Тогда:

```bash
make cli C='dags unpause hw_basic_batch_inference'
docker compose exec -T scheduler airflow dags trigger hw_basic_batch_inference --run-id first-run --conf '{"business_date":"2026-09-01"}'
```

Расписания у базового DAG нет, поэтому unpause сам ничего не запускает. Дождитесь окончания run в UI, затем проверьте SQL:

```bash
docker compose exec -T warehouse psql -U etl -d warehouse < warehouse/check.sql
```

Каждый следующий trigger требует нового run ID. Пока задания 2-5 не реализованы, run упадёт в той задаче, которая первой вызывает заглушку.

## Команды и устройство

- `make up`: сборка и запуск сервисов. Первый раз нужен интернет для образов и пакетов; версии Python-пакетов закреплены constraints.
- `make health`: состояние БД Airflow, scheduler, triggerer и DAG processor.
- `make check`: импорт DAG и проверка его структуры, настроек и params без запуска бизнес-логики.
- `make unit`: только чистые проверки модели и контрактов, отдельный контейнер без запуска сервисов. Сначала нужен собранный образ (`docker compose build scheduler`).
- `make test`: все тесты, включая настоящий PostgreSQL. Запускается после make up; не запускайте одновременно с экспериментами ручного изменения схемы.
- `make down`: остановить текущий проект, сохранить базы и историю.
- `make clean`: остановить текущий проект, удалить его БД (включая историю запусков Airflow), Docker-volume логов и include/artifacts. Исходные данные и ваш код не удаляет и не возвращает изменённые fixture к исходным значениям.

`dags/` - ваш DAG и код обработки; `data/` - входные данные и модель; `include/` - health check и создаваемые артефакты; `tests/` - проверки; `warehouse/` - схема и диагностический SQL; `source_api/` - локальный HTTP-источник; `tools/` - вспомогательные команды. Полный набор признаков и expected results перечислены в задании.

Не запускайте несколько копий одновременно на одинаковых портах. Для параллельного стенда скопируйте `.env.example` в `.env` и измените три порта. Имена volumes зависят от имени Compose-проекта, а оно по умолчанию совпадает с именем папки. Если две копии лежат в папках с одинаковым именем, задайте во второй копии в `.env` свой `COMPOSE_PROJECT_NAME`, иначе они будут использовать одни и те же базы. На Linux после копирования замените `AIRFLOW_UID` на свой (`id -u`).

Это локальный учебный стенд: UI без пароля, известные пароли PostgreSQL, localhost-only порты. В публичной сети так разворачивать нельзя от слова совсем.
