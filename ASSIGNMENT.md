# ДЗ 1. Ежедневный батч-инференс модели оттока

## Цель

Модель ежедневно оценивает вероятность ухода клиентов. Обученную логистическую регрессию вам уже принесли, осталось самое "простое": нужно написать DAG Airflow и функции обработки дневной выгрузки, то есть получить признаки и модель по HTTP, проверить данные, рассчитать предсказания пачками и атомарно заменить результат за день в PostgreSQL.

Обучать модель, делать API онлайн-инференса, ставить CUDA и подключаться к внешним облакам не нужно. Batch inference здесь означает обработку конечной дневной выборки пачками размера `batch_size`: модель вызывается векторно на каждую пачку, а не HTTP-запросом на каждого клиента.

## Постановка

Дано:

- Airflow 3.3.1, PostgreSQL 16, HTTP-источник, модель и синтетические данные; всё запускается через Docker Compose, он уже написан за вас. Подключения `source_api` (HTTP-источник) и `warehouse` (БД результатов) уже настроены.
- Обученная логистическая регрессия лежит в `data/models/v1.json`, процедура обучения описана в `tools/generate_fixture.py`, запускать его не требуется.
- Дневные выборки: 1 сентября 125 строк, 2 сентября 129, 3 сентября 97. Все даты относятся к 2026 году и зоне Europe/Moscow.
- Четыре признака в фиксированном порядке: `age`, `tenure_months`, `monthly_spend`, `support_tickets_30d`. Идентификатор и дата в матрицу признаков не входят.
- В `dags/batch_common.py` есть вспомогательные функции: выбор даты (`business_date`), SHA-256 (`digest`), проверка модели (`validate_model`), инференс (`predict`) и обмен файловыми артефактами (`save`/`read`). Благодаря артефактам в XCom хранится только ссылка вида `{"sha256": "<hex>"}`, а не вся выборка.

Нужно написать:

- **Задание 1.** DAG `hw_basic_batch_inference` в `dags/hw_basic.py`. В шаблоне файл содержит только комментарий; граф, настройки и тела задач пишете вы.
- **Задания 2-5.** Четыре функции в `dags/batch_common.py` (сейчас бросают `NotImplementedError`).

## Запуск

```bash
make up
make health
make check

```

UI: http://localhost:8090 (без пароля). Источник данных: http://localhost:8001/basic/2026-09-01.json. Порты открыты только на localhost, пароли в Compose учебные. `make up` создаёт служебную БД Airflow, отдельную БД результатов и запускает `api-server`, `scheduler`, `dag-processor`, `triggerer` и HTTP-источник `source-api`.

После задания 1 `make check` проходит и тесты графа зеленеют, но тесты заданий 2-5 остаются красными до реализации функций. Успешный импорт DAG не означает, что работа готова.

## Задание 1. DAG hw_basic_batch_inference

Ниже перечислено, что проверяют тесты. Стиль кода (TaskFlow или классические операторы, имена функций и переменных) на ваше усмотрение. Фиксированы идентификаторы, настройки и поведение.

### Правила оформления

- Используйте публичный API Airflow 3: `airflow.sdk` (`dag`/`DAG`, `task`, `Param`, `BaseHook` и т. п.) и `PostgresHook` из `airflow.providers.postgres`. Не импортируйте `airflow.models.*` и устаревший `airflow.decorators`.
- **Никакого ввода-вывода при импорте модуля.** `dag-processor` постоянно перечитывает файл, поэтому на верхнем уровне допустимы только импорты, константы и объявление DAG. HTTP-запросы, чтение подключений и файлов, соединения с БД допустимы только внутри задач.
- Не создавайте пулы, подключения и переменные из кода DAG, потому что они часть окружения.

### Настройки DAG

| Параметр | Значение | Зачем |
|---|---|---|
| `dag_id` | `hw_basic_batch_inference` | по нему работают `make check`, тесты и команды ниже |
| `start_date` | 1 сентября 2026, 00:00, Europe/Moscow | бизнес-зона дат |
| `schedule` | `None` | только ручной запуск с параметрами |
| `catchup` | `False` | |
| `max_active_runs` | `1` | два run не пишут один день одновременно |
| `tags` | `homework`, `basic` | |

Параметры запуска (`params`) объявляются через `Param` с JSON-схемой, чтобы UI и CLI отвергали неверные значения до старта задач:

- `business_date`: по умолчанию `"2026-09-01"`, тип `string`, формат `date`.
- `batch_size`: по умолчанию `32`, тип `integer`, `minimum` 1, `maximum` 1000.

`default_args` для всех задач: `retries=2`, `retry_delay` 5 секунд, `execution_timeout` 2 минуты. Таймаут обязателен, потому что зависший HTTP-запрос или блокировка в БД будут держать вам worker'а до Нового года.

### Задачи

Ровно три задачи `extract`, `infer`, `publish` с зависимостями `extract >> infer >> publish`. Других задач и связей нет. Зависимости следуют из передачи данных: каждая задача получает ссылку, возвращённую предыдущей. Правило запуска `all_success`.

Вспомогательные функции `batch_common`:

| Функция | Что делает |
|---|---|
| `business_date(explicit, interval_start)` | строка `YYYY-MM-DD`: явный параметр либо дата начала интервала в Москве |
| `digest(content: bytes)` | SHA-256 точных байтов, hex-строка |
| `save(obj) -> ref` | сохраняет JSON-совместимый объект в артефакт, возвращает ссылку-словарь `{"sha256": "<hex>"}` |
| `read(ref) -> obj` | принимает такой словарь, читает артефакт и проверяет хэш |
| `validate_model(model)` | проверяет порядок признаков, размерности и коэффициенты модели, при ошибке выдаст `ValueError`|
|`predict(rows, model)`|векторный инференс на списке строк, возвращает `[{"customer_id", "score", "label"}]`, `score` округлён до 8 знаков|
| `validate_rows`, `infer_batches`, `validate_predictions`, `replace_day` | задания 2-5 |

**`extract`**: загрузка данных.

- Вход: только контекст запуска. Дата определяется через `business_date(...)` из параметра `business_date` и `data_interval_start` контекста (если его нет, передаётся `None`).
- Базовый URL источника берётся из поля `host` подключения `source_api` (через `BaseHook.get_connection`). Не зашивайте `localhost:8001`, на паре обсудили, что внутри контейнеров адрес другой.
- Запрос `GET {host}/basic/{day}.json` с явным таймаутом 10 секунд и проверкой HTTP-статуса (например, `raise_for_status()`): ответ 404/503 должен ронять задачу, а не превращаться в пустой день. Если `business_date` в ответе не совпадает с запрошенной датой, бросайте `ValueError`.
- Запрос модели `GET {host}/models/v1.json` по тем же правилам. `model_sha256` считается через `digest` от точных байтов тела ответа, а не от повторно сериализованного JSON.
- Выход: `save(...)` объекта с ключами `business_date`, `rows`, `model` (разобранный JSON модели), `model_sha256`. В XCom только ссылка.
- Повторы наследуются (`retries=2`), потому что сетевые сбои и ответы с `status_code` 5xx временные. Ошибка несовпадения даты тоже будет повторена, это допустимо, отдельно отключать для неё повторы не требуется.

**`infer`**: проверка и батч-инференс.

- Вход: ссылка из `extract` и параметр `batch_size` из контекста.
- Прочитайте артефакт, вызовите `validate_rows` (задание 2), затем `infer_batches` (задание 3) с моделью из артефакта и `batch_size`, затем `validate_predictions` (задание 4) со списком `customer_id` проверенных строк.
- Выход: `save(...)` объекта с ключами `business_date`, `model_version` (`"v1"`), `predictions`, `model_sha256`. В XCom только ссылка.
- Повторы: переопределите `retries=0` на уровне задачи. Ошибка данных детерминирована, повтор даст тот же результат и лишь задержит сигнал.

**`publish`**: публикация.

- Вход: ссылка из `infer`.
- Прочитайте результат. Внутри задачи получите новое соединение `PostgresHook(postgres_conn_id="warehouse").get_conn()`, вызовите `replace_day(conn, business_date, model_version, predictions)` (задание 5) и закройте соединение в `finally`. До вызова `replace_day` не выполняйте на этом соединении запросов (см. задание 5).
- Выход: словарь `business_date`, `model_version`, `rows` (число опубликованных строк).
- Повторы: как обычно `retries=2`. Они безопасны, потому что `replace_day` заменяет снимок дня целиком.

ВАЖНО! Хранить в XCom строки клиентов, модель или предсказания, объединять шаги в одну задачу, вызывать модель вне `infer` НЕЛЬЗЯ.

## Задания 2-5: функции в dags/batch_common.py

### 2. validate_rows(rows, day)

Возвращает исходный список только после проверки всех строк. Пустой список запрещён. `customer_id` должен быть непустой строкой, уникальной в пределах дня. `business_date` каждой строки совпадает с `day`. Признаки должны быть конечными числами, строки, `bool`, NaN и бесконечности запрещены. Диапазоны включают границы: возраст 18-100, стаж 0-240 месяцев, траты 0-10000, обращения 0-100. Не заменяйте плохое значение нулём и не отбрасывайте клиента молча, ошибка должна остановить инференс до публикации. При нарушении бросайте `ValueError`; при отсутствии обязательного ключа допустим `KeyError`.

### 3. infer_batches(rows, model, batch_size)

`batch_size` должен быть целым от 1 до 1000, иначе бросайте `ValueError`, в том числе для `True` (помните про особенности питона) и нецелых значений вроде `2.5`. Последовательно режьте уже проверенный список на непересекающиеся части и на каждую вызывайте `predict(batch, model)` ровно один раз. Порядок клиентов сохраняется, последний, вероятно неполный, батч надо обязательно обработать. Используйте уже загруженный `model`, не открывайте модель внутри цикла.

Для 125 строк и размера 32 нужно четыре вызова с длинами 32, 32, 32, 29. Для размера 16 - восемь: семь по 16 строк и один на 13. Вызов модели на каждого клиента, несколько вызовов на всей выборке или один вызов на весь день не засчитываются. Здесь подразумевается, что `batch_size` всё ещё может принимать значения от 1 до 1000, просто вам запрещено игнорировать его как параметр. То есть, если `batch_size=1`, то ОК делать вызов на каждого клиента. Аналогично и если `batch_size>=clients`, можно сделать один вызов. По дальнейшему тексту я думаю и так понятно, что мы все же сфокусированы на случаях, когда `1 < batch_size < clients`. Выведите в лог номер и фактический размер каждой пачки. Проверка структуры модели внутри `predict` допустима, это не повторная загрузка.

### 4. validate_predictions(predictions, expected_ids)

Количество и множество `customer_id` должны точно совпадать с `expected_ids`, дубликаты запрещены. `score` - конечное число от 0 до 1 включительно. `label` - значение типа `int`, равное 0 или 1 (`bool` запрещён, как и в задании 2) и совпадающее с `int(score >= 0.5)`. Функция ничего не публикует. При нарушении бросайте `ValueError`.

### 5. replace_day(conn, day, model_version, predictions)

До изменения БД запретите пустой `predictions`. Пустая публикация должна сохранить прежний снимок. На пустой список бросайте `ValueError`, в сообщении которого есть слово `Empty` с заглавной буквы, например `ValueError("Empty predictions")`: тест проверяет это через `match="Empty"`. В одной транзакции:

1. Возьмите транзакционную advisory-блокировку по паре "дата, версия модели": `pg_advisory_xact_lock(hashtextextended(%s, 0))` с параметром `day + ':' + model_version`.
2. Удалите прежние строки этой даты и версии.
3. Вставьте новые строки параметризованным SQL.
4. Зафиксируйте транзакцию только после всех успешных вставок. Исключение должно вызывать rollback и пробрасываться наружу.

Границы транзакции задавайте через `with conn.transaction()`, в psycopg 3 он делает commit при успехе и rollback при исключении, но не закрывает соединение (в отличие от `with conn`). Внешнюю транзакцию BEGIN/COMMIT он открывает только на соединении без уже начатой транзакции. Если до него был выполнен запрос, создаётся SAVEPOINT, и внешняя транзакция не фиксируется. Поэтому `publish` передаёт свежее соединение, весь SQL функции выполняется внутри `transaction()`, а закрывает соединение `publish` в `finally`. Не делайте отдельный commit после DELETE и не подставляйте данные в SQL через f-string.

Почему недостаточно `ON CONFLICT DO UPDATE`: если во второй версии выгрузки исчез клиент, его старый прогноз останется. Публикуется полный снимок дня, поэтому нужна замена набора. Первичный ключ гарантирует уникальность на уровне БД, а транзакция - целостность всего набора.


В UI проверьте граф из трёх задач, дождитесь успешного run `basic-32` и откройте логи `infer`: размеры пачек 32, 32, 32, 29. У `extract` в `Storage - XCom` значение `return_value` содержит SHA-256. Массива клиентов в таблицах Airflow быть не должно. Если после `unpause` CLI ещё показывает DAG как paused, проверьте состояние в UI.

```bash
docker compose exec -T scheduler airflow dags trigger hw_basic_batch_inference --run-id basic-16 --conf '{"business_date":"2026-09-01","batch_size":16}'
docker compose exec -T warehouse psql -U etl -d warehouse < warehouse/check.sql
```

Ожидаемо для 1 сентября, v1: 125 строк, из них 44 с меткой 1, средний score 0.38077391 (округление до 8 знаков). Первые оценки: c0000=0.20572767, c0001=0.46234233, c0002=0.24357032. После повторного запуска строк по-прежнему 125. Второй run запускайте после завершения первого, каждый раз с новым `run-id`.

Запуск с `"batch_size": 0` должен быть отвергнут схемой параметров до начала задач.

`tests/test_dags.py` проверяет идентификаторы, связи, настройки, параметры и политику повторов DAG. Удалять или ослаблять выданные тесты нельзя.

## Остановка
